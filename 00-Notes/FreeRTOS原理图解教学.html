01

上电那一刻发生了什么

按下复位键，CPU 内部没有"操作系统"，也没有"main 函数"。它只做一件事：从地址 0x00000000 处取两个字。而 PY32C882 的 Flash 被映射到 0x08000000，所以实际读的是 0x08000000。

知识点 1.1复位不是"从 0 开始"，而是"从向量表开始"

向量表 = 一个 48 字的数组（Cortex-M0+），每个字是一个地址。CPU 硬编码使用前两个：[0] → MSP、[1] → PC。字段顺序不能改，改了上电就跑飞。

知识点 1.2两个"堆/栈"完全是两回事

名字在哪定义谁用本工程实测
Stack_Size（MSP 主栈）启动文件 startup_py32c882xx.s中断、异常、启动代码0x800 = 2 KB（移植时从 0x400 提上来的）
Heap_Size同上malloc()（MicroLIB）0x200 = 512 B，FreeRTOS 根本不用它
configTOTAL_HEAP_SIZEFreeRTOSConfig.hFreeRTOS 的 pvPortMalloc8192 B，是 heap_4.c 里一个 静态数组（进 .bss）
任务栈 ×NxTaskCreate() 第 3 个参数各任务自己（走 PSP）128 字 = 512 B（单位是"字"！）

最容易搞错的一点：FreeRTOS 的内存不是从启动文件的 Heap_Size 里来的。heap_4.c 里有一个 static uint8_t ucHeap[configTOTAL_HEAP_SIZE]，它作为普通全局变量进 .bss，跟着 SRAM 一起被清零。两者互不相干。

02

CPU 的 16 个寄存器和两个栈

理解任务切换，只需要搞清"现场"是什么。现场 = 16 个寄存器的值。把它们原样存下来、再把另一个任务上次存的值装回去，就是一次上下文切换。

知识点 2.1SP 只有一个名字，却有两个实体

汇编里写 SP，CPU 内部其实有两个寄存器 MSP / PSP，由 CONTROL[1]（SPSEL）决定当前用哪个。所以：

  • mrs r0, psp —— 读出"另一个"栈指针，是 FreeRTOS 里最关键的一条指令之一；
  • Handler 模式下硬件强制走 MSP，写 SPSEL 也无效 —— 这条保证了中断安全。
03

异常、向量表与优先级

在 Cortex-M 的世界里，"中断"和"出错"是同一类东西，统称异常。它们共用一张向量表、共用一套优先级规则、共用一套进出流程。搞清楚这一套，任务切换就只是它的一个特例。

异常号名字谁产生在 FreeRTOS 里的角色
1Reset复位引脚/上电上电入口
2NMI不可屏蔽中断一般不用
3HardFault所有错误的最终归集处你上次踩的那个：取指/访问错误、除零(CM0+ 无)、非法指令
11SVCallSVC 指令★M3/M4 用它启动第一个任务；CM0+ 端口不用它
14PendSV软件写 ICSR 置位★真正的任务切换在这里执行
15SysTickSysTick 计数器到 0★RTOS 的心跳（1ms）
16 – 47IRQ0 – IRQ31外设（UART/TIM/EXTI…）你的业务中断

知识点 3.1为什么内核异常必须是"最低优先级"

PendSV 和 SysTick 是 RTOS 的后台工作：一个负责切换任务、一个负责数时间。它们必须让所有外设中断先跑完，否则会出现灾难性后果：

  • 如果切换能打断一个正在处理数据的 UART 中断，切回来时外设状态已经变了；
  • 如果 SysTick 能打断高优先级外设中断，节拍处理会与业务的临界区互相踩。

所以内核把这两个异常设成 优先级 3（最低），业务中断用 0 ~ 2。这条规则在 CM0+ 上就是全部——它没有 BASEPRI 可以做"部分屏蔽"。

实战对照

本工程实测：SysTick->LOAD = 7999（节拍对）、SHPR3 = 0xC0C00000（优先级对）。如果你哪天改完时钟发现 LOAD = 7999 却 SHPR3 = 0，说明内核还没接管。

04

SysTick：时间从哪来

任务能"延时 250ms 后自己醒来"，是因为有一个硬件在替它数时间。这个硬件就是内核自带的 SysTick 定时器——它不是 PY32 芯片加的外设，而是 Cortex-M 内核的一部分（所有 M 核都有）。

这就是你上次 HardFault 的战场

HAL_Init() 会把 SysTick 打开并允许中断（为了给 HAL_Delay / HAL_GetTick 供时基）。但此时 FreeRTOS 的调度器还没启动，它的内部数据结构是空的。这期间任何一个 tick 进来，就会走进一张还没初始化好的表里。第 8 章会把整个事故完整复盘。

05

一次异常的完整进出

这是整篇最重要的一节。理解了"异常进出时硬件替你做了什么"，你就会明白：任务切换根本不是什么魔法，而是把这个机制借来用了一次。

进入异常：硬件自动压 8 个字

当异常被响应，CPU 不执行任何指令就先做这几件事：把当前要保护的 8 个寄存器压到当前使用的栈上 → 从向量表取异常处理函数的地址 → 把 PC 跳过去。压栈顺序是固定的：

退出异常：靠 LR 里的"暗号"

异常发生瞬间，LR 被硬件改写成特殊值 EXC_RETURN（不是普通返回地址）。异常处理函数返回时，只要 bx 跳回这个值，硬件就知道"这是要退出异常"，于是自动弹栈、恢复现场。

EXC_RETURN 值含义弹栈时用哪个栈常见于
0xFFFFFFF1返回 Handler 模式（异常嵌套）MSP中断嵌套
0xFFFFFFF9返回 线程模式MSP普通裸机代码、启动阶段
0xFFFFFFFD返回 线程模式PSP★返回任务（RTOS 里最常见）
核心结论

"切换任务"就是"让硬件从另一个栈上弹帧"。因为弹哪个栈由 EXC_RETURN 的 bit2 决定（1 → PSP），所以只要在 PendSV 里把 PSP 换成新任务的栈，再 bx 回去，硬件就会老老实实把新任务的现场装进 CPU —— 一个字节的指令都不用改，全靠硬件。

这就解释了 FreeRTOS 里那两处看起来奇怪的写法：pxPortInitialiseStack() 在任务栈上"手工伪造一个帧"，prvPortStartFirstTask() 最后用 bx 跳进任务函数。

知识点 5.1tail-chaining 与 late-arrival

  • tail-chaining（背靠背）：一个异常刚处理完，另一个已挂起 → 硬件不弹栈再压栈，直接跳到下一个处理函数。省掉的正是那 8 个字的时间。
  • late-arrival（晚到抢占）：异常刚进入压栈阶段，一个更高优先级的异常来了 → 硬件改去执行高优先级的，压栈动作复用。
  • 对 RTOS 的意义：频繁发生的中断（比如 1ms 的 SysTick）大部分时间都走了 tail-chaining，代价远小于"完整进出一次"。

知识点 6.1任务的"优先级"是软件概念，和硬件的 4 级无关

CM0+ 的硬件优先级只有 4 级，但 configMAX_PRIORITIES 可以设 8、16、32。原因：

  • 硬件优先级决定的是 中断能不能互相抢占；
  • 任务优先级只是"就绪链表的下标"。任务是靠 PendSV 这个唯一的切换点轮流跑的，根本不经过硬件优先级比较。

所以本工程 configMAX_PRIORITIES = 8，而外设中断只能用 0 ~ 2。

上下文切换全过程

下面这 3 段代码全部来自本工程的实际文件：FreeRTOS\Source\portable\RVDS\ARM_CM0\port.c。看懂它们，你就彻底懂了 RTOS 最核心的 200 行。

片段 ① pxPortInitialiseStack()：创建任务时"伪造"一个现场

xTaskCreate() 内部会调用它，作用是在新任务栈的顶部手工摆出一个"刚被中断打断"的帧：

StackType_t * pxPortInitialiseStack( StackType_t * pxTopOfStack,
                                     TaskFunction_t pxCode, void * pvParameters )
{
    pxTopOfStack--;
    *pxTopOfStack = portINITIAL_XPSR;                 /* ① xPSR = 0x01000000（bit24 = Thumb 位，必须为 1）*/
    pxTopOfStack--;
    *pxTopOfStack = ( StackType_t ) pxCode;           /* ② PC = 任务函数的入口地址 */
    pxTopOfStack--;
    *pxTopOfStack = ( StackType_t ) prvTaskExitError; /* ③ LR = 万一任务函数 return 了去哪 */
    pxTopOfStack -= 5;                                /* ④ 跳过 R12, R3, R2, R1 四格 */
    *pxTopOfStack = ( StackType_t ) pvParameters;     /* ⑤ R0 = 任务参数（就是 xTaskCreate 的 pvParameters）*/
    pxTopOfStack -= 8;                                /* ⑥ 空出 R11…R4 八格（首次运行没有旧值）*/
    return pxTopOfStack;
}

要点这段代码是"面向硬件契约"写的

它压栈的顺序和位置，必须一个字节都不差地对上 8 字硬件帧的布局（R0 在低地址、xPSR 在高地址），因为将来硬件会按这个格式去弹。xTaskCreate 第 3 个参数为什么是"字数"？因为这里减的是一个个 StackType_t（= uint32_t）。

片段 ② prvPortStartFirstTask()：启动第一个任务

调度器准备好之后，由它把 CPU"交给"第一个任务。注意：这里没有 SVC 指令。M3/M4 教程里讲的"SVC 启动第一个任务"在 CM0+ 上不成立——源码注释写明了原因：M0 没有 VTOR，无法重新定位初始栈值，所以改用"直接设置 PSP + bx"。

ldr r3, = pxCurrentTCB     ; r3 = &pxCurrentTCB
ldr r1, [ r3 ]
ldr r0, [ r1 ]             ; r0 = TCB->pxTopOfStack（指向 R4 槽）
adds r0, # 32              ; ★跳过 R4–R11：8 个字 × 4 字节 = 32
msr psp, r0                ; ★PSP 指向 R0 槽 = 硬件帧的起点
movs r0, # 2
msr CONTROL, r0            ; ★SPSEL = 1：线程模式从此改用 PSP
isb
pop { r0 - r5 }            ; 弹出 R0,R1,R2,R3,R12,LR
mov lr, r5                 ; LR 里装的是 EXC_RETURN（异常返回暗号）
pop { r3 }                 ; r3 = PC = 任务函数入口
pop { r2 }                 ; 丢弃 xPSR
cpsie i                    ; 开中断
bx r3                      ; ★跳进任务函数，任务从此开始跑

片段 ③ xPortPendSVHandler()：运行时切换（全篇核心）

每次要换任务时，内核只做一件事：往 ICSR 寄存器写一位，把 PendSV 挂起。等所有更高优先级的中断都干完了，PendSV 才被响应 —— 于是"切换"永远发生在最安全的时刻。

mrs r0, psp                ; r0 = 当前任务的 PSP（指向硬件帧 R0 槽）
ldr r3, = pxCurrentTCB
ldr r2, [ r3 ]             ; r2 = pxCurrentTCB（即将被换下的任务）

subs r0, # 32              ; ↓ 向下让出 32 字节给 R4–R11
str r0, [ r2 ]             ; ★把新的栈顶存回 旧TCB->pxTopOfStack
stmia r0 !, { r4 - r7 }    ; 压 R4–R7
mov r4, r8                 ; CM0 的指令限制：高寄存器要先搬到低寄存器
mov r5, r9
mov r6, r10
mov r7, r11
stmia r0 !, { r4 - r7 }    ; 压 R8–R11 → 旧任务现场保存完毕（16 字）

push { r3, r14 }           ; 保存 r3 和 LR(EXC_RETURN)，因为下面要调 C 函数
cpsid i                    ; 关中断（CM0 上这是"全局关"，没有 BASEPRI）
bl vTaskSwitchContext      ; ★★唯一的"决策"：挑下一个任务、更新 pxCurrentTCB
cpsie i
pop { r2, r3 }             ; r2 = 新TCB地址, r3 = EXC_RETURN

ldr r1, [ r2 ]
ldr r0, [ r1 ]             ; r0 = 新任务的栈顶（指向它的 R4 槽）
adds r0, # 16              ; 跳过 R4–R7，定位到 R8 槽
ldmia r0 !, { r4 - r7 }    ; 恢复 R8–R11
mov r8, r4
mov r9, r5
mov r10, r6
mov r11, r7

msr psp, r0                ; ★★PSP = 新任务的硬件帧起点
subs r0, # 32              ; 回退到 R4 槽
ldmia r0 !, { r4 - r7 }    ; 恢复 R4–R7 → 新任务现场装载完毕

bx r3                      ; ★★★用 EXC_RETURN 返回！
                           ;     硬件从新 PSP 弹 8 字帧 → PC 变成新任务的下一条指令
一句话总结整个机制

任务切换 = 保存旧任务的 16 个寄存器到它的栈 → 调用 C 函数决定下一个跑谁 → 从新任务的栈把 16 个寄存器装回来 → 用 bx EXC_RETURN 让硬件"以为"只是从一次中断里返回。

硬件完全被骗过去了：它以为自己在退出一个普通异常，于是乖乖地从 PSP 弹出那 8 个字并继续执行 —— 而那个 PC 属于另一个任务。没有任何"特殊跳转"指令，一切建立在异常返回机制之上。

事故复盘：为什么"停在初始化函数里"却进了 HardFault

这是你在本工程真实踩到的坑，也是 HAL 库工程接 RTOS 最容易中的一枪。两条时序线放一起对比就清楚了：

修复：让 SysTick 的归属"分阶段"

思路不是"压缩初始化时间"（那是靠运气），而是让两种状态都有明确的处理者：

/* Inc\FreeRTOSConfig.h —— 不做名字映射，让 port.c 保留原名 xPortSysTickHandler */
/* #define xPortSysTickHandler              SysTick_Handler */

/* Src\py32c882_it.c */
extern void xPortSysTickHandler(void);

void SysTick_Handler(void)
{
  if (xTaskGetSchedulerState() == taskSCHEDULER_NOT_STARTED)
  {
    HAL_IncTick();            /* 裸机阶段：维持 HAL_GetTick / HAL_Delay / HAL 超时 */
  }
  else
  {
    xPortSysTickHandler();    /* 已启动：交给 FreeRTOS 节拍 */
  }
}

为什么这样绝对安全不存在"中间态"

vTaskStartScheduler() 是先关中断（tasks.c:2026），再依次设 xNextTaskUnblockTime、xSchedulerRunning（2036/2037），最后才进 xPortStartScheduler()。没有中断能观察到"已判定为运行中、但内部还没初始化好"的状态。

顺带的好处：调度器启动之前 HAL_GetTick() / HAL_Delay() 照常可用（真实产品的初始化代码常这么用），启动之后由 tick 钩子接着喂 —— 两边都是 1ms，无缝衔接。

09

并发、临界区与 ISR 三范式

多个任务 + 多个中断，会同时碰同一块内存。RTOS 提供的"保护手段"在 CM0+ 上和 M3/M4 有本质区别，这是抄教程最容易抄错的地方。

知识点 9.1临界区是可嵌套的，靠一个计数器

裸机时代"关中断/开中断"只能成对出现，多层调用就乱了。FreeRTOS 用一个计数解决：

void vPortEnterCritical( void )   /* port.c:262 */
{
    portDISABLE_INTERRUPTS();      /* cpsid i */
    uxCriticalNesting++;           /* 嵌套层数 +1 */
}
void vPortExitCritical( void )    /* port.c:271 */
{
    configASSERT( uxCriticalNesting );
    uxCriticalNesting--;
    if( uxCriticalNesting == 0 )   /* ★只有回到 0 才真正开中断 */
    {
        portENABLE_INTERRUPTS();   /* cpsie i */
    }
}

调试时把 uxCriticalNesting 加到 Watch 窗口：稳态必须是 0。长期不为 0 说明某处漏了配对的 taskEXIT_CRITICAL()，系统时间会变慢（中断开不回来，tick 进不来）。

ISR → 任务的三种标准范式

中断里"做决策、做重活"是禁忌。正确姿势只有三种，按开销从大到小：

ISR 里的铁律
  • 只能用名字带 ...FromISR 的 API：xQueueSendFromISR / xSemaphoreGiveFromISR / xTaskNotifyFromISR。
  • 唤醒标志变量必须初始化：BaseType_t xHigherPriorityTaskWoken = pdFALSE;
  • 退出前一定要 portYIELD_FROM_ISR(xHigherPriorityTaskWoken); —— 否则"被唤醒的高优先级任务"要等到下一次 tick 才轮到。
  • ISR 里禁止：vTaskDelay、HAL_Delay、Flash 写、长 printf。
  • CM0+ 的 ARM_CM0 端口没有优先级校验函数，所以你在 ISR 里误用非 FromISR 版本 API 不会触发断言，而是偶发数据错乱 —— 只能靠纪律。

❌ 错误：UartTask / TimTask / GpioTask（这是把中断搬到任务里）。
✅ 正确：SensorTask（采集+滤波）、JudgeTask（安全判定，优先级最高）、CommTask（协议收发）、LogTask（打印/存储）、MgrTask（喂狗+低功耗）。

做法 2优先级只有 3 ~ 4 档，安全最高

本工程实测可用的分法：安全判定 3 > 业务/通信 2 > 日志/显示 1 > 空闲 0。别用优先级去解决"谁先谁后"的同步问题，那应该用队列/信号量。

做法 3栈大小用"水位"倒推，不用猜

  • 单位是字：128 = 512 字节；
  • 含 printf / vTaskList（内部用 sprintf）的任务给 256 字；
  • 用 uxTaskGetStackHighWaterMark() 看剩余，留 30% 余量再定稿；
  • 本工程实测：led 任务剩余 118 字、log 任务剩余 185 字（都在安全区）。

做法 4周期任务用 vTaskDelayUntil，别用 vTaskDelay

写法含义累积漂移
vTaskDelay(250)从"现在"开始睡 250ms会漂移（执行时间被累加进去）
vTaskDelayUntil(&last, 250)睡到"上次唤醒时刻 + 250ms"不漂移（以起点为基准）

你的 50ms 采样、1 秒打印、定时喂狗都属于这类，一律用 vTaskDelayUntil。

本工程实测资源占用

Program Size: Code=9576 RO-data=652 RW-data=128 ZI-data=11176
→ Flash = 9576 + 652 ≈ 10.2 KB（256 KB 的 4%）；RAM = 128 + 11176 ≈ 11.0 KB（32 KB 的 34%，其中 8 KB 是 FreeRTOS 堆）。
上板现象：LED3 保持 2Hz 翻转，串口每秒一行状态、每 5 秒一张任务表（含 IDLE 行 —— 它在，说明调度器确实在工作）。

手段 3：CM0+ 的 HardFault 怎么定位（它没有 CFSR！）

和 M3/M4 教程最大的不同

网上讲 "HardFault 看 SCB->CFSR 就知道原因" 的教程，在 CM0+ 上全部无效 —— CM0+ 只有 HardFault，没有 CFSR / HFSR / BFAR / MMFAR。你唯一能拿到的是压栈帧（第 5 章那张图）。

把下面这段临时放进 HardFault_Handler，然后看那几个全局变量：

volatile uint32_t hf_r0,hf_r1,hf_r2,hf_r3,hf_r12,hf_lr,hf_pc,hf_psr,hf_exc_return;

void HardFault_Handler(void)
{
    __asm volatile (
        " tst lr, #4        \n"   /* LR(EXC_RETURN) bit2：0=用 MSP，1=用 PSP */
        " ite eq            \n"
        " mrseq r0, msp     \n"
        " mrsne r0, psp     \n"
        " ldr r1, =hf_r0    \n"
        " ldmia r0!, {r2-r6}\n"   /* 取 R0,R1,R2,R3,R12 */
        " stmia r1!, {r2-r6}\n"
        " ldmia r0!, {r2-r6}\n"   /* 取 LR,PC,xPSR */
        " stmia r1!, {r2-r6}\n"
        " mov r6, lr        \n"
        " str r6, [r1]      \n"   /* 保存 EXC_RETURN */
        " b .               \n"
    );
}
看到的说明
hf_pc出错的那条指令地址 → 拿 .map 或反汇编查它属于哪个函数
hf_exc_return = 0xFFFFFFF9故障发生在线程模式 + MSP → 初始化代码 / 裸机部分出错
hf_exc_return = 0xFFFFFFFD故障发生在任务里（PSP） → 多半是任务栈溢出或野指针
在 HardFault_Handler 看 Call Stack若是 xPortSysTickHandler 调下来的 → 调度器/节拍问题；若是 vTaskSwitchContext → 链表/栈被写坏

用这套方法看第 8 章那次事故，会看到 hf_pc 落在 xTaskIncrementTick() 里、hf_exc_return = 0xFFFFFFF9 —— 与"启动前 SysTick 抢跑"的结论完全吻合。

12

自测题（10 题）

能不看答案答出 8 题，这套原理就算真正过了一遍。点击题号展开答案。

1. 上电后 CPU 执行的第一条指令地址是怎么来的？

硬件从向量表第 1 个字（0x08000004）读出 Reset_Handler 的地址并跳过去；第 0 个字被用来装载 MSP。这两个字是硬件约定，任何软件都还没运行。

2. 为什么 CM0+ 上 taskENTER_CRITICAL() 会关掉全部中断？

因为 CM0+ 只有 PRIMASK（总闸），没有 BASEPRI。FreeRTOS 的 CM0 端口用 cpsid i 实现临界区，没有"只屏蔽低于某优先级"的能力。推论：CM0+ 上 ISR 必须极短，configMAX_SYSCALL_INTERRUPT_PRIORITY 这个宏在 CM0+ 上不生效。

3. SHPR3 里写的是 255，为什么调试器读回 0xC0？

CM0+ 只用 2 位表示优先级（4 级），即每个 8 位优先级字段里只有高 2 位（bit7:6）被实现。写 0b1111_1111，实际落地 0b1100_0000 = 0xC0，即优先级 3（最低）。 SHPR3 = 0xC0C00000 说明 PendSV 和 SysTick 都是最低优先级。

4. HAL 工程接 RTOS 时，HAL_IncTick() 为什么要搬家？搬到哪？

因为原来的 SysTick_Handler 要让位给 RTOS。如果只是注释掉，HAL 侧不会报错，但 HAL_GetTick() 永远是 0 → HAL_Delay() 死等不返回、所有 HAL 超时立即失效。搬到 vApplicationTickHook()（configUSE_TICK_HOOK 必须为 1），让 HAL 时基与 RTOS 节拍同源。

5. 任务栈参数写 128，是多少字节？含 printf 的任务该给多少？

128 的单位是字（StackType_t = uint32_t）= 512 字节。含 printf 或 vTaskList（内部 sprintf）的任务建议 256 字 = 1KB，并留 30% 余量。本工程 log 任务给的就是 256 字。

6. 任务切换时，硬件帮你保存了几个寄存器？剩下谁保存？

硬件自动压 8 个：R0–R3、R12、LR、PC、xPSR（共 32 字节）。R4–R11 硬件不管，由 PendSV 里的 stmia 手工压入 —— 所以完整帧是 16 个字 = 64 字节。

7. bx r3 里的 r3 装的是什么？为什么跳完就"换了任务"？

装的是 EXC_RETURN（异常返回暗号，如 0xFFFFFFFD）。bx 到它就等于"告诉硬件：我要退出异常"。硬件于是按 bit2 决定从 PSP 弹 8 字帧 —— 而 PSP 在上一句刚被设成新任务的栈，于是 PC 被换成新任务的下一条指令。切换 = 伪造一次异常返回。

8. CM0+ 的 FreeRTOS 端口用 SVC 启动第一个任务吗？

不用。port.c 里 vPortSVCHandler() 是空函数（注释写着 *"no longer used, but retained for backward compatibility"*），启动第一个任务走 prvPortStartFirstTask()：手工设置 PSP → 写 CONTROL 切栈 → pop 出寄存器 → bx 进任务函数。原因见源码注释：M0 没有 VTOR，无法定位初始栈值。

9. 为什么 vTaskDelay(1000) 在那次事故里只等了约 111ms？

那不是事故现象，而是主频配置错误的典型症状：板子实际 72MHz，却把 configCPU_CLOCK_HZ 写成 8000000 → SysTick 重载 = 7999，实际节拍 = 72MHz/8000 = 9kHz → 1000 个 tick 只花约 111ms。验证方法：调试器看 SystemCoreClock 必须等于 configCPU_CLOCK_HZ。

10. 为什么周期任务要用 vTaskDelayUntil 而不是 vTaskDelay？

vTaskDelay(n) 从"现在"起睡 n 个 tick，任务本身执行的时间会被累加进去，周期越来越长；vTaskDelayUntil(&last, n) 睡到"上次唤醒时刻 + n"，以上次唤醒为基准，不累积漂移。你的 50ms 采样、1s 打印、定时喂狗都必须用后者。
