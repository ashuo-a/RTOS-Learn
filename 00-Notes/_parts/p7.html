手段 3：CM0+ 的 HardFault 怎么定位（它没有 CFSR！）

和 M3/M4 教程最大的不同

网上讲 "HardFault 看 SCB->CFSR 就知道原因" 的教程，在 CM0+ 上全部无效 —— CM0+ 只有 HardFault，没有 CFSR / HFSR / BFAR / MMFAR。你唯一能拿到的是压栈帧（第 5 章那张图）。

把下面这段临时放进 HardFault_Handler，然后看那几个全局变量：

volatile uint32_t hf_r0,hf_r1,hf_r2,hf_r3,hf_r12,hf_lr,hf_pc,hf_psr,hf_exc_return;

void HardFault_Handler(void)
{
    __asm volatile (
        " tst lr, #4        \n"   /* LR(EXC_RETURN) bit2：0=用 MSP，1=用 PSP */
        " ite eq            \n"
        " mrseq r0, msp     \n"
        " mrsne r0, psp     \n"
        " ldr r1, =hf_r0    \n"
        " ldmia r0!, {r2-r6}\n"   /* 取 R0,R1,R2,R3,R12 */
        " stmia r1!, {r2-r6}\n"
        " ldmia r0!, {r2-r6}\n"   /* 取 LR,PC,xPSR */
        " stmia r1!, {r2-r6}\n"
        " mov r6, lr        \n"
        " str r6, [r1]      \n"   /* 保存 EXC_RETURN */
        " b .               \n"
    );
}
看到的说明
hf_pc出错的那条指令地址 → 拿 .map 或反汇编查它属于哪个函数
hf_exc_return = 0xFFFFFFF9故障发生在线程模式 + MSP → 初始化代码 / 裸机部分出错
hf_exc_return = 0xFFFFFFFD故障发生在任务里（PSP） → 多半是任务栈溢出或野指针
在 HardFault_Handler 看 Call Stack若是 xPortSysTickHandler 调下来的 → 调度器/节拍问题；若是 vTaskSwitchContext → 链表/栈被写坏

用这套方法看第 8 章那次事故，会看到 hf_pc 落在 xTaskIncrementTick() 里、hf_exc_return = 0xFFFFFFF9 —— 与"启动前 SysTick 抢跑"的结论完全吻合。

自测题（10 题）

能不看答案答出 8 题，这套原理就算真正过了一遍。点击题号展开答案。

1. 上电后 CPU 执行的第一条指令地址是怎么来的？

硬件从向量表第 1 个字（0x08000004）读出 Reset_Handler 的地址并跳过去；第 0 个字被用来装载 MSP。这两个字是硬件约定，任何软件都还没运行。

2. 为什么 CM0+ 上 taskENTER_CRITICAL() 会关掉全部中断？

因为 CM0+ 只有 PRIMASK（总闸），没有 BASEPRI。FreeRTOS 的 CM0 端口用 cpsid i 实现临界区，没有"只屏蔽低于某优先级"的能力。推论：CM0+ 上 ISR 必须极短，configMAX_SYSCALL_INTERRUPT_PRIORITY 这个宏在 CM0+ 上不生效。

3. SHPR3 里写的是 255，为什么调试器读回 0xC0？

CM0+ 只用 2 位表示优先级（4 级），即每个 8 位优先级字段里只有高 2 位（bit7:6）被实现。写 0b1111_1111，实际落地 0b1100_0000 = 0xC0，即优先级 3（最低）。 SHPR3 = 0xC0C00000 说明 PendSV 和 SysTick 都是最低优先级。

4. HAL 工程接 RTOS 时，HAL_IncTick() 为什么要搬家？搬到哪？

因为原来的 SysTick_Handler 要让位给 RTOS。如果只是注释掉，HAL 侧不会报错，但 HAL_GetTick() 永远是 0 → HAL_Delay() 死等不返回、所有 HAL 超时立即失效。搬到 vApplicationTickHook()（configUSE_TICK_HOOK 必须为 1），让 HAL 时基与 RTOS 节拍同源。

5. 任务栈参数写 128，是多少字节？含 printf 的任务该给多少？

128 的单位是字（StackType_t = uint32_t）= 512 字节。含 printf 或 vTaskList（内部 sprintf）的任务建议 256 字 = 1KB，并留 30% 余量。本工程 log 任务给的就是 256 字。

6. 任务切换时，硬件帮你保存了几个寄存器？剩下谁保存？

硬件自动压 8 个：R0–R3、R12、LR、PC、xPSR（共 32 字节）。R4–R11 硬件不管，由 PendSV 里的 stmia 手工压入 —— 所以完整帧是 16 个字 = 64 字节。

7. bx r3 里的 r3 装的是什么？为什么跳完就"换了任务"？

装的是 EXC_RETURN（异常返回暗号，如 0xFFFFFFFD）。bx 到它就等于"告诉硬件：我要退出异常"。硬件于是按 bit2 决定从 PSP 弹 8 字帧 —— 而 PSP 在上一句刚被设成新任务的栈，于是 PC 被换成新任务的下一条指令。切换 = 伪造一次异常返回。

8. CM0+ 的 FreeRTOS 端口用 SVC 启动第一个任务吗？

不用。port.c 里 vPortSVCHandler() 是空函数（注释写着 *"no longer used, but retained for backward compatibility"*），启动第一个任务走 prvPortStartFirstTask()：手工设置 PSP → 写 CONTROL 切栈 → pop 出寄存器 → bx 进任务函数。原因见源码注释：M0 没有 VTOR，无法定位初始栈值。

9. 为什么 vTaskDelay(1000) 在那次事故里只等了约 111ms？

那不是事故现象，而是主频配置错误的典型症状：板子实际 72MHz，却把 configCPU_CLOCK_HZ 写成 8000000 → SysTick 重载 = 7999，实际节拍 = 72MHz/8000 = 9kHz → 1000 个 tick 只花约 111ms。验证方法：调试器看 SystemCoreClock 必须等于 configCPU_CLOCK_HZ。

10. 为什么周期任务要用 vTaskDelayUntil 而不是 vTaskDelay？

vTaskDelay(n) 从"现在"起睡 n 个 tick，任务本身执行的时间会被累加进去，周期越来越长；vTaskDelayUntil(&last, n) 睡到"上次唤醒时刻 + n"，以上次唤醒为基准，不累积漂移。你的 50ms 采样、1s 打印、定时喂狗都必须用后者。
