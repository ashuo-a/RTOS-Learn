## 0. 先破三个常见误解（尤其你看 F103 教程一定被带偏）

| 常见说法（来自 CM3 教程） | CM0+ 上的真相 |
|---|---|
| "FreeRTOS 用 `SVC 0` 启动第一个任务" | ❌ **CM0 端口根本不用 SVC**。`port.c:179` 的 `vPortSVCHandler()` 是个**空函数**，注释明写 *"no longer used, but retained for backward compatibility"*；`xPortStartScheduler()` 直接调用 `prvPortStartFirstTask()`。**【源码实证 port.c:179-214, 220-239】** |
| "临界区用 `BASEPRI = configMAX_SYSCALL_INTERRUPT_PRIORITY`，只屏蔽低优先级中断" | ❌ **CM0+ 没有 BASEPRI**。临界区就是 `CPSID i`（关掉**所有**中断）。而且 `configMAX_SYSCALL_INTERRUPT_PRIORITY` 在 ARM_CM0 端口里**一次都没被引用**。**【源码实证：grep 该宏在 port.c / portmacro.h 中 0 命中】** |
| "内核优先级由 `configKERNEL_INTERRUPT_PRIORITY` 决定" | ❌ CM0 端口把 PendSV/SysTick 优先级**硬编码为最低**：`portNVIC_PENDSV_PRI = 255 << 16`、`portNVIC_SYSTICK_PRI = 255 << 24`，用了 `portMIN_INTERRUPT_PRIORITY (255UL)`，宏根本没参与运算。**【源码实证 port.c:50-52, 223-225】** |

这三条是 CM0+ 上 RTOS 移植最容易"照抄出错"的地方，本笔记后面会逐个讲清原因。

## 1. 硬件模型速览：ARMv6-M 的"家底"

PY32L090 / PY32C882 是 **Cortex-M0+，ARMv6-M 架构**。它比 CM3/M4 简化得多，但**RTOS 需要的机制它一个不少**。

### 1.1 寄存器组

| 寄存器 | 说明 | RTOS 关注点 |
|---|---|---|
| R0–R12 | 通用寄存器 | R0–R3 传参；**R4–R11 是"被调用者保存"**，所以任务切换必须手动保存它们 |
| R13 = **MSP / PSP** | 两个物理栈指针，同一时刻只有一个"当前 SP" | ★ 任务用 PSP，异常用 MSP → 这就是"每个任务独立栈"的硬件基础 |
| R14 = LR | 链接寄存器；**异常发生时 LR = EXC_RETURN** | ★ 决定"异常返回后回到哪个栈、哪个模式" |
| R15 = PC | 程序计数器 | 切换时保存点 |
| xPSR | APSR(标志) + IPSR(异常号) + EPSR(T 位) | 任务初始 xPSR 必须由软件构造 |

### 1.2 两种模式 × 两个栈

```
        ┌───────────────── Thread 模式（跑你的任务代码）─────────────────┐
        │  使用 MSP (CONTROL.SPSEL=0)  →  裸机程序/启动阶段             │
        │  使用 PSP (CONTROL.SPSEL=1)  →  ★ RTOS 的每个任务            │
        └──────────────────────────────────────────────────────────────┘
                                    │ 中断/异常
                                    ▼
        ┌───────────────── Handler 模式（跑 ISR）──────────────────────┐
        │  ★ 强制使用 MSP，无法改成 PSP                                 │
        └──────────────────────────────────────────────────────────────┘
```

**CONTROL 寄存器（CM0+）**：

| 位 | 名称 | 作用 |
|---|---|---|
| bit0 | nPRIV | 0=特权，1=非特权 |
| bit1 | SPSEL | 0=用 MSP，1=用 PSP |
| ~~bit2~~ | ~~FPCA~~ | **CM0+ 没有这位（无 FPU）**，CM4F 才有 |

FreeRTOS 在启动第一个任务时就是写 CONTROL=2 切到 PSP（见 §6.2 汇编 `movs r0, #2 / msr CONTROL, r0`）。

### 1.3 特权与"跑飞"

CM0+ 支持非特权模式，但裸机程序和 FreeRTOS 都跑在特权态。**别指望非特权模式兜底**——MPU 在 CM0+ 上是可选项，PY32L090 手册第 35 章只提到 NVIC/DWT/BPU，没有 MPU 相关章节，**按没有 MPU 对待**。也就是说：**没有任何硬件能阻止一个野指针踩掉别的任务栈**。这就是为什么后面要开 `configCHECK_FOR_STACK_OVERFLOW`。

## 2. 异常向量表：PY32L090 的实际编号

ARMv6-M 的异常编号是架构固定的，**用异常号而不是"优先级"来区分**：

| 异常号 | 名称 | 说明 | PY32L090 启动文件 |
|---|---|---|---|
| — | 初始 SP | 向量表第 0 项 = `_estack` | `startup_py32l090.s:75` |
| 1 | Reset | 复位 | |
| 2 | NMI | 不可屏蔽（含 RCC 时钟安全） | |
| 3 | **HardFault** | ★ ARMv6-M **只有这一个 Fault** | `HardFault_Handler` |
| 11 | **SVCall** | `SVC` 指令触发 | `SVC_Handler`（startup:88） |
| 14 | **PendSV** | ★ 可挂起的系统服务 —— **任务的"换场"就发生在这** | `PendSV_Handler`（startup:91） |
| 15 | **SysTick** | ★ 系统节拍 | `SysTick_Handler`（startup:92） |
| 16+ | IRQ0..31 | 外设中断（手册第 10 章：**32 个可屏蔽中断通道**） | `WWDG_IRQHandler`... |

⚠️ **ARMv6-M 只有 HardFault**，没有 MemManage / BusFault / UsageFault，也**没有 CFSR / HFSR / BFAR / MMFAR** 这些故障状态寄存器。
后果：CM0+ 上的 HardFault **查不到"哪个地址非法、什么原因"**，只能靠人工解析压栈帧里的 PC/LR 反推。这一条直接影响你后面阶段 4 的"HardFault 定位"手段设计——在 CM3 上便捷的 `SCB->CFSR` 分析法在你这颗片子上**不适用**。

### 2.1 ⚠️ CM0+ 没有 VTOR —— 你的 IAP 必须知道这件事

CM3/M4 有 `SCB->VTOR`，可以把向量表搬到任意地址（IAP 的标准做法）。**ARMv6-M 没有 VTOR**，中断向量表**永远从 0x0000_0000 取**。

PY32L090 的替代方案（手册第 3 章 3.1.4「启动模式」+ 第 8 章 SYSCFG）：
- 硬件层面：`BOOT0` 引脚 + 选项字节里的 `nBOOT1`、`BOOT_LOCK` 决定 0x0000_0000 映射到谁（Flash 主存储区 / 6.5KB 系统存储器 / SRAM）
- 软件层面：`SYSCFG_CFGR1.MEM_MODE[1:0]` 可以做**运行时的物理重映射**，绕过硬件 BOOT 选择（手册 08_SYSCFG 第 32-35 行、157-158 行）

**对你的实际意义**：`vPortStartFirstTask()` 的注释专门为此写了一句（port.c:192-194）：
> *"The MSP stack is not reset as, unlike on M3/4 parts, there is no vector table offset register that can be used to locate the initial stack value. Not all M0 parts have the application vector table at address 0."*

即：CM3 端口能靠 VTOR 找到真正应用的栈顶去重置 MSP，**CM0 端口做不到**，因此你的 IAP 跳转必须自己保证 0x0000_0000 处就是应用的向量表（或 MEM_MODE 已重映射），否则 MSP 还是 Bootloader 的——这是个隐患点，留到阶段 5 深挖。

## 3. 异常进入：硬件默默做了什么（★全篇最核心）

当 SysTick 或外设中断触发、且优先级允许抢占时，**硬件在没有任何软件参与的情况下**完成：

**第 1 步：压栈（8 个字，32 字节）**

压到"当前栈"（正文任务用 PSP）上，顺序固定（**低地址 → 高地址**）：

| 偏移 | 内容 | 说明 |
|---|---|---|
| +0 | R0 | |
| +4 | R1 | |
| +8 | R2 | |
| +12 | R3 | |
| +16 | R12 | 这 4 个是"调用者保存"，所以硬件替你存 |
| +20 | LR (R14) | ★ 返回地址（被打断处的下一条指令） |
| +24 | PC (R15) | ★ 异常返回后从这里继续 |
| +28 | xPSR | 含 APSR 标志位 |

> 这就是所谓 **"hardware-saved frame"**。**R4–R11 硬件不管**，必须软件自己存——这正是 FreeRTOS 要在 `xPortPendSVHandler` 里手写 8 条存取指令的原因（§6.4）。
>
> ⚠️ **对齐**：ARMv6-M 上异常进入**强制 8 字节对齐**（不可关闭）。若 SP 未对齐，硬件插入一个填充字，并在 xPSR 的 bit9 标记。所以**任务栈必须是 8 字节对齐的**，这也解释了 FreeRTOS 里 `portBYTE_ALIGNMENT = 8`（portmacro.h:80）。
>
> ARMv6-M 微架构上这 8 个字分两步压栈（影响 late-arrival 的判定窗口），但**架构可见结果与上表一致**。

**第 2 步：取向量**
从向量表读出异常号对应的入口地址（HardFault→0x0C，SVCall→0x2C，PendSV→0x38，SysTick→0x3C）。

**第 3 步：更新 LR = EXC_RETURN**
这一步是"RTOS 双栈"的关键机制，LR 不再是普通返回地址，而是一个**魔法值**：

| EXC_RETURN | 含义 | 何时出现 |
|---|---|---|
| `0xFFFFFFF1` | 返回 **Handler 模式**，用 **MSP** | 嵌套异常返回 |
| `0xFFFFFFF9` | 返回 **Thread 模式**，用 **MSP** | 打断裸机程序（用 MSP 的任务） |
| `0xFFFFFFFD` | 返回 **Thread 模式**，用 **PSP** | ★ **打断 RTOS 任务**——最常看到的值 |
| ~~0xFFFFFFE1/E9/ED~~ | 带 FPU 上下文的版本 | **CM0+ 不存在**（CM4F/CM7 才有） |

**第 4 步：切到 Handler 模式，跳转执行**
Handler 模式**一律用 MSP**，所以：**ISR 栈 vs 任务栈天然隔离**，任务栈不管开多大都不会被 ISR 挤爆——这是 RTOS 相比裸机的巨大优势，也是你裸机时代"栈要预留多少"难题的解药。

**额外机制（性能来源）**
- **Tail-chaining（尾链）**：一个 ISR 刚退出、下一个已挂起 → 硬件跳过 8 字出栈+入栈，直接跳过去
- **Late-arrival（迟到）**：压栈期间来了更高优先级中断 → 直接改道去执行高优先级的，**不重复压栈**

### 3.1 退出：`bx lr` 为什么就"回到任务"了？

因为此时 LR 里是 `EXC_RETURN`。执行 `bx lr`（或 `bx r3`，r3 里存的也是它，见 §6.4）时，硬件识别出这是特殊值，于是：
1. 从 EXC_RETURN 指定的栈（bit2=0 用 MSP，bit2=1 用 PSP）弹出那 8 个字
2. 恢复到对应的模式和特权级
3. 跳回 PC 所指位置继续执行

⭐ **这就是"任务切换"的全部秘密**：只要在异常处理过程中**偷偷把栈里那 8 个字换成另一个任务的**，硬件就会"毫无察觉地"跳到另一个任务去执行。FreeRTOS 干的就是这件事。

## 4. 优先级：CM0+ 只有 4 级，且没有 BASEPRI

手册第 10 章原文：**"4 个可编程的优先级（2 位中断优先级）"**。

| 项 | CM0+ (ARMv6-M) | CM3/M4 (ARMv7-M) |
|---|---|---|
| 优先级位宽 | **2 位 → 4 级**（0 最高，3 最低） | 通常 4 位 → 16 级 |
| 可屏蔽中断 | 32 个 | 240 个 |
| 优先级寄存器 | `SHPR2`/`SHPR3`（异常）、`NVIC_IPR[]`（外设） | 同左，但位宽更大 |
| **BASEPRI** | ❌ **不存在** | ✅ 存在 |
| 关中断手段 | **只有 PRIMASK（`CPSID i`）= 关全部** | `CPSID i` 或 `BASEPRI` 按级别屏蔽 |

### 4.1 FreeRTOS 把 PendSV/SysTick 放在最低优先级

**【源码实证 port.c:50-52】**
```c
#define portMIN_INTERRUPT_PRIORITY  ( 255UL )
#define portNVIC_PENDSV_PRI         ( portMIN_INTERRUPT_PRIORITY << 16UL )   /* SHPR3 高 16 位 = PendSV */
#define portNVIC_SYSTICK_PRI        ( portMIN_INTERRUPT_PRIORITY << 24UL )   /* SHPR3 高 8 位 = SysTick */
```
**【源码实证 port.c:222-225】** `xPortStartScheduler()` 开头：
```c
portNVIC_SHPR3_REG |= portNVIC_PENDSV_PRI;   /* PendSV  → 最低优先级 */
portNVIC_SHPR3_REG |= portNVIC_SYSTICK_PRI;  /* SysTick → 最低优先级 */
```
（硬件只实现 2 位，所以写进去的 255 实际落到优先级 3 = 最低）

**为什么要最低？——这是个精妙设计，面试爱问**
1. **PendSV 最低** → 切换请求会被"拖延"到**所有 ISR 都执行完**才发生。这样**任何中断都不会被任务切换延迟**，实时性由中断优先级保证，而不是靠 RTOS。
2. **SysTick 最低** → 节拍中断也要给外设中断让路，避免 1ms 定时器打断高频串口接收。
3. 由于两者同级且都最低，它们之间不会互相抢占，切换逻辑天然安全。

### 4.2 临界区 = 关掉一切

**【源码实证 port.c:262-268】**：
```c
void vPortEnterCritical( void )
{
    portDISABLE_INTERRUPTS();          /* ← portmacro.h:113 = __disable_irq() = CPSID i */
    uxCriticalNesting++;
    __dsb( portSY_FULL_READ_WRITE );
    __isb( portSY_FULL_READ_WRITE );
}
```
**【源码实证 port.c:283-299】** ISR 里用的版本也是读 PRIMASK 再关：
```c
__asm uint32_t ulSetInterruptMaskFromISR( void )
{
    mrs r0, PRIMASK    /* 先保存旧的屏蔽状态 */
    cpsid i            /* 再关全部中断——注意不是 BASEPRI！ */
    bx lr
}
```

**推论（对你产品的 3 条硬纪律）**
1. **任何临界区都会屏蔽全部中断** → 包括你的 UART DMA 完成、EXTI 掉电检测、50ms ADC 触发！
2. **内核内部的临界区也算**：`xQueueSend`、信号量 Give/Take 内部都有 `portENTER_CRITICAL()`，所以频繁操作队列/信号量本身就在制造中断延迟。
3. → **纪律 1**：ISR 尽量短，只置标志/发通知；
   **纪律 2**：别在任务里写"大循环 + 临界区"（比如整个 Flash 擦写过程包在临界区里 —— 你的日志写入必须重新设计）；
   **纪律 3**：高频事件用 DMA 降频，别用"高频中断 + 每次发队列"。

> **对比记忆**：CM3 上你可以做到"只屏蔽低优先级中断，高优先级（如电机急停）照常响应"；**CM0+ 上做不到**。这是 CM0+ 跑 RTOS 最大的实时性损失，也是选型时该知道的代价。

### 4.3 一个"没有 assert"的坑

**【源码实证】** ARM_CM0 端口里**没有 `vPortValidateInterruptPriority()`**（CM3/CM4 端口有）。所以：
- 你在 ISR 里误用 `xQueueSend()`（非 FromISR 版本）→ **CM0 上不会有 `configASSERT` 拦你**
- 后果是**偶发、极难复现的数据损坏**，而不是立刻断在断言处

→ 纪律：**中断里只允许 `...FromISR` 系列 API**，这条只能靠人自觉，硬件和内核都不帮你兜底。

## 5. SysTick：节拍从哪来

| 寄存器 | 地址 | 作用 |
|---|---|---|
| `SYST_CSR` | 0xE000E010 | bit0 ENABLE、bit1 TICKINT、bit2 CLKSOURCE、bit16 COUNTFLAG |
| `SYST_RVR` | 0xE000E014 | 重装载值（24 位，最大 0xFFFFFF） |
| `SYST_CVR` | 0xE000E018 | 当前值（写任意值清零） |
| `SYST_CALIB` | 0xE000E01C | 校准值 |

**手册第 10 章两条关键原文**：
> "SysTick 校准值被设为 6000，通过 SysTick 时钟置为 6MHz（max fHCLK/8），给出了 **1ms** 的参考 time base。"
> **"在进入睡眠或者停止低功耗前，需要关闭 systick 的中断。"** ← ★ 厂商明确写了这条

**【源码实证 port.c:390-396】** FreeRTOS 的配置逻辑（72MHz 内核时钟、1kHz 节拍）：
```c
portNVIC_SYSTICK_CTRL_REG = 0UL;                                  /* 先停掉、清干净 */
portNVIC_SYSTICK_CURRENT_VALUE_REG = 0UL;
portNVIC_SYSTICK_LOAD_REG = ( configSYSTICK_CLOCK_HZ / configTICK_RATE_HZ ) - 1UL;
    /* = 72,000,000 / 1000 - 1 = 71999 → 1ms 一次中断 ✓ */
portNVIC_SYSTICK_CTRL_REG = CLK_BIT | INT_BIT | ENABLE_BIT;
```
默认 `configSYSTICK_CLOCK_HZ = configCPU_CLOCK_HZ`（port.c:73-76），即 **SysTick 用内核时钟不分频**。

⚠️ **注意手册那句警告 vs FreeRTOS 的 tickless**：默认的 FreeRTOS **每秒要醒 1000 次**，你的 STOP 模式根本进不去。必须开 `configUSE_TICKLESS_IDLE`，而 tickless 的核心实现（port.c:404-618）正是"**进睡眠前关掉 SysTick、算出下次唤醒时间、唤醒后补 tick**"——**和你手册那句警告完全对应**。这就是阶段 4 的主战场，也是你相对其他 RTOS 学习者的**最大优势区**。

顺带：`portMISSED_COUNTS_FACTOR = 94`（port.c:63-65）是官方给的一个"估摸值"，用来补偿 SysTick 停走期间损失的计数——说明**tickless 天然存在微小时间漂移**，这是它的固有代价，不是你配错了。

## 6. ★ 任务切换全过程（源码级）

### 6.1 创建任务时，栈被"做"成什么样

`pxPortInitialiseStack()`（port.c:142-159）逐行看：

```c
StackType_t * pxPortInitialiseStack( StackType_t * pxTopOfStack,
                                     TaskFunction_t pxCode, void * pvParameters )
{
    pxTopOfStack--;                                   /* ← 偏移字（对齐用） */
    *pxTopOfStack = portINITIAL_XPSR;                 /* xPSR = 0x01000000 */
    pxTopOfStack--;
    *pxTopOfStack = ( StackType_t ) pxCode;           /* PC = 任务入口函数 */
    pxTopOfStack--;
    *pxTopOfStack = ( StackType_t ) prvTaskExitError; /* LR = 任务返回时的兜底 */
    pxTopOfStack -= 5;                                /* R12, R3, R2, R1 */
    *pxTopOfStack = ( StackType_t ) pvParameters;     /* R0 = 参数 ★ */
    pxTopOfStack -= 8;                                /* R4..R11 */

    return pxTopOfStack;   /* 这个值存进 TCB 的第一个成员 */
}
```

**手工构造的帧布局（从低地址到高地址）：**

```
        低地址 ────────────────────────────────────────────────► 高地址
        ┌────┬────┬───┬───┬───┬───┬───┬───┬───┬───┬───┬───┬───┬────┐
        │R4-7│R8-11│R0 │R1 │R2 │R3 │R12│LR │PC │xPSR│ 对齐字        │
        │← 8 个字 →│←─────── 与硬件压栈帧完全同构的 8 个字 ──────│
        └────┴────┴───┴───┴───┴───┴───┴───┴───┴───┴───┴───┴───┴────┘
         ▲                                                     ▲
         │                                                   栈顶(8字节对齐)
      栈底
      17 个字 = 68 字节（R4-R11 由软件管，其余 9 个字模拟硬件帧+对齐）
```

三个必须理解的点：

1. **`xPSR = 0x01000000`** —— bit24 是 **T 位（Thumb）**。CM0+ 只支持 Thumb 指令，**这一位必须是 1**，否则任务一启动立刻 HardFault。这是"手搓任务现场"最容易漏的一位。
2. **`R0 = pvParameters`** —— 任务函数是普通 C 函数，第一个参数走 R0。所以"传参"的本质就是"把参数塞进软件构造的帧里"。
3. **`LR = prvTaskExitError`** —— 任务函数如果 return 了，就落到这个函数里触发断言/死循环。**任务函数永远不能 return**（要退出得 `vTaskDelete(NULL)`）。
4. **那个"偏移字"** 是栈顶指针被向下对齐到 8 字节的产物（见 `tasks.c` 里对 `pxTopOfStack` 的 `& ~portBYTE_ALIGNMENT_MASK` 掩码）——就是为了满足 §3 里说的"ARMv6-M 异常进入强制 8 字节对齐"。
   > 🔎 冷知识：因为这个掩码，**栈深度取偶数个字会白白丢掉最后 4 字节**（如 128 字 = 512B，实际只能用 508B）；取**奇数**（127 字 = 508B）则刚好不浪费。`configMINIMAL_STACK_SIZE` 不是字节数而是**字数**（CM0 上 1 字 = 4 字节），这点搞错会直接把栈开成 1/4。

### 6.2 启动第一个任务：不用 SVC（★CM0 特有）

**【源码实证 port.c:186-214】**
```asm
prvPortStartFirstTask:
    ldr r3, = pxCurrentTCB      ; r3 = &pxCurrentTCB
    ldr r1, [ r3 ]              ; r1 = pxCurrentTCB (TCB 指针)
    ldr r0, [ r1 ]              ; r0 = TCB 第一个成员 = 任务栈顶（指向 R4 槽）
    adds r0, # 32               ; 跳过 8 个字（R4-R11）→ 指向 R0 槽
    msr psp, r0                 ; ★ PSP = R0 槽地址（从此任务用 PSP）
    movs r0, # 2                ; CONTROL.SPSEL = 1
    msr CONTROL, r0             ; ★ 切到 PSP 栈
    isb
    pop { r0 - r5 }             ; 弹出 R0,R1,R2,R3,R12,LR （LR = prvTaskExitError → 存入 r5）
    mov lr, r5                  ; LR 就位
    pop { r3 }                  ; r3 = PC = 任务入口函数
    pop { r2 }                  ; 弹出并丢弃 xPSR
    cpsie i                     ; ★ 开中断（第一个任务开始接管）
    bx r3                       ; ★ 跳到任务函数，从此再也没有"回到调用者"这回事
```

**注意最后那段：它不是在"调用"任务，而是直接 `bx` 跳进去**——这个函数**永远不会返回**，`xPortStartScheduler()` 里它后面的 `return 0;` 是死代码（port.c:237 注释 *"Should not get here!"*）。

**对比 CM3**：CM3 端口会把栈顶写进 MSP、然后执行 `svc 0`，让 SVC 异常"顺便"完成现场恢复与开中断。CM0 端口把这个过程**拆成了纯软件操作**（因为 CM0 的 SVC 能力较弱，且 `vPortSVCHandler` 已废弃）。
→ **所以你在 `FreeRTOSConfig.h` 里那三行映射中，`SVC_Handler` 那行其实是可选的**，但 `PendSV_Handler` 和 `SysTick_Handler` **必须有**（否则落到启动文件的死循环里）。

### 6.3 切换的两种触发路径

```
【路径 A：任务主动让出】
  任务调用 vTaskDelay / xQueueReceive(带超时) / taskYIELD()
        ↓
  vPortYield()  ──  port.c:250-259
        ↓  写 ICSR(0xE000ED04) 的 bit28 (PENDSVSET)
  ★ 只是"挂起 PendSV 异常"，并不立即切换

【路径 B：时间片用完】
  SysTick 中断  ──  xPortSysTickHandler()  port.c:350-370
        ↓  xTaskIncrementTick() 返回 pdTRUE（说明有任务需要被唤醒/该轮转了）
        ↓  同样写 ICSR bit28 挂起 PendSV

两条路径最后都汇合到 PendSV：
        ↓
  因为 PendSV 优先级 = 最低  →  ★ 等所有 ISR 都跑完，
  且此时不再有更高优先级中断  →  硬件才真正跳进 xPortPendSVHandler
```

这就是为什么 `portYIELD()` 里只写了一个寄存器、然后立刻 `__dsb()/__isb()`（port.c:257-258）——真正的切换"稍后由硬件排队执行"。

### 6.4 `xPortPendSVHandler` 逐行解剖（★全篇重点）

**【源码实证 port.c:302-347】**，注解是我加的：

```asm
xPortPendSVHandler:
    mrs r0, psp                 ; ① r0 = 任务的 PSP（硬件已压完 8 字帧，PSP 指向 R0 槽）

    ldr r3, = pxCurrentTCB      ; ② r3 = &pxCurrentTCB
    ldr r2, [ r3 ]              ;    r2 = pxCurrentTCB（当前任务的 TCB）

    subs r0, # 32               ; ③ 为 R4-R11 腾出 32 字节
    str r0, [ r2 ]              ; ④ ★把新栈顶写回 TCB 第一个成员（pxTopOfStack）
    stmia r0 !, { r4 - r7 }     ;    ★手工保存 R4-R7，r0 += 16
    mov r4, r8                  ; ⑤ 高寄存器不能直接 stmia，先搬到低寄存器
    mov r5, r9
    mov r6, r10
    mov r7, r11
    stmia r0 !, { r4 - r7 }     ;    ★手工保存 R8-R11

    push { r3, r14 }            ; ⑥ 保护 r3(=&pxCurrentTCB) 和 LR(=EXC_RETURN, 0xFFFFFFFD)
    cpsid i                     ; ⑦ 关中断：不允许被打断（链表操作必须原子）
    bl vTaskSwitchContext       ; ⑧ ★★★ 真正"选下一个任务"：更新 pxCurrentTCB
    cpsie i
    pop { r2, r3 }              ;    r2 = &pxCurrentTCB, r3 = EXC_RETURN

    ldr r1, [ r2 ]              ; ⑨ r1 = 新任务 TCB（★此时 pxCurrentTCB 已被换掉）
    ldr r0, [ r1 ]              ;    r0 = 新任务的栈顶（指向它的 R4 槽）
    adds r0, # 16               ; ⑩ 先跳到 R8 槽
    ldmia r0 !, { r4 - r7 }     ;    恢复 R8-R11（借道 r4-r7）
    mov r8, r4
    mov r9, r5
    mov r10, r6
    mov r11, r7

    msr psp, r0                 ; ⑪ ★PSP 改成新任务的（此时 r0 已指向新任务的 R0 槽）
    subs r0, # 32               ;    回退到 R4 槽
    ldmia r0 !, { r4 - r7 }     ;    恢复 R4-R7

    bx r3                       ; ⑫ ★★用 EXC_RETURN 返回 → 硬件从【新的 PSP】
                                ;    弹出 8 字帧 → 跳进新任务的 PC，继续跑！
```

**这 12 步里，真正的"魔法"只有第 ④、⑧、⑪、⑫ 步**：
- ④ 把"旧任务的栈顶"保存进 TCB
- ⑧ 换掉 `pxCurrentTCB`（此时"当前任务"已经变成新任务了）
- ⑪ 把 PSP 指向新任务的栈
- ⑫ 用 EXC_RETURN 返回 —— **硬件完全不知道任务换了人**，它只会老老实实从 PSP 弹出 8 个字、跳回那个 PC。对硬件来说，"就是一次普通的异常返回"。

**这就是 RTOS 最优雅的地方：任务切换不是"特殊的跳转"，而是"伪造一次异常返回"。**

**两个细节问答：**
- **为什么要 `cpsid i`（⑦）？** 因为 PendSV 是最低优先级，**任何更高优先级的中断都能抢占它**。如果在 `vTaskSwitchContext()` 遍历就绪链表时被打断、而那个 ISR 又恰好改了链表，就会破坏内核数据。CM3 上这里用 BASEPRI 精确屏蔽；**CM0+ 只能全关**。
- **为什么 `push {r3, r14}` 再 `pop {r2, r3}`？** `bl` 会覆盖 LR（存放返回地址），而 LR 里原来是珍贵的 EXC_RETURN。所以先存起来，`bl` 后再恢复到 r3，最后用 `bx r3` 返回。**这就是最后那句 `bx r3` 的由来**，不是"随便放到一个寄存器里"。

### 6.5 一次完整切换的时序全景

```
  任务A (Thread/PSP)                        ISR / 异常 (Handler/MSP)
  ──────────────────────────────────────────────────────────────────
  LDR  r1,[r0]  ← 正在执行
        │
        │ ① SysTick 中断（或 A 自己 yield 触发 PendSV）
        ▼
  ┌─ 硬件：把 R0-R3,R12,LR,PC,xPSR 压到【A的PSP栈】 ──┐
  │  硬件：LR = 0xFFFFFFFD (EXC_RETURN)              │
  │  硬件：切 Handler 模式，用 MSP                    │
  │  硬件：跳 SysTick_Handler (0x3C)                  │
  └──────────────────────────────────────────────────┘
        │
        ▼  xPortSysTickHandler(): xTaskIncrementTick() → pdTRUE
           ICSR.PENDSVSET = 1  ──┐
        │                        │ ② 所有 ISR 跑完
        ▼ 硬件异常返回（8字出栈，A 继续跑一小段）
        │                        │
        │◄───────────────────────┘ ③ ★PendSV 才被"放行"（最低优先级）
        ▼
  ┌─ 硬件：再次压栈（A 的 8 字帧，因为异常又来了）──┐
  │  硬件：跳 xPortPendSVHandler (0x38)            │
  └────────────────────────────────────────────────┘
        │
        ▼ ④ 保存 A 的 R4-R11 → A 的 pxTopOfStack 存回 TCB_A
        ▼ ⑤ vTaskSwitchContext(): pxCurrentTCB = TCB_B   ← 换场完成
        ▼ ⑥ 从 TCB_B 恢复 B 的 R4-R11，PSP = B 的栈指针
        ▼ ⑦ bx r3 (EXC_RETURN) ──┐
        │                         │
  ┌─────◄─────────────────────────┘ 硬件：从【B 的 PSP】弹出 8 字帧
  │  硬件：跳进 B 的 PC，B 毫不知情地继续跑
  └─────────────────────────────────────────────────┘
        ▼
  任务B (Thread/PSP) 继续执行
```

**成本核算**：一次切换 = 硬件 8 字压栈 + 软件 8 字存取 + 链表操作。
在 72MHz 的 CM0+ 上，一次切换大约几十微秒量级（无 FPU、无 cache、Flash 取指），**1000Hz 节拍下光切换开销就吃掉 ~1% CPU 是正常的**——这解释了为什么后面要关心 `uxTaskGetSystemState` 的 CPU 占用率。

## 8. 自测题（能答上来才算过关）

1. 异常进入时硬件压哪 8 个寄存器？为什么不压 R4–R11？
2. `EXC_RETURN = 0xFFFFFFFD` 是什么意思？它在哪个寄存器里？
3. 为什么 Handler 模式只用 MSP？这对任务栈大小有什么好处？
4. 任务初始 xPSR = `0x01000000`，这个 1 是什么？置 0 会怎样？
5. 启动第一个任务时，CM0 端口用不用 SVC？为什么 `vPortSVCHandler` 是空的？
6. `xPortPendSVHandler` 里的 `bx r3`，r3 里到底是什么？
7. 为什么 FreeRTOS 把 PendSV 和 SysTick 都设为**最低**优先级？有什么好处？
8. CM0+ 上没有 BASEPRI 意味着什么？对你的串口接收中断有什么影响？
9. 为什么 `vPortEnterCritical()` 在 CM0 上等于 `CPSID i`，在 CM3 上却不等于？
10. 任务函数不小心 `return` 了会怎样？为什么？
11. `configMINIMAL_STACK_SIZE = 128` 是多少字节？为什么"含 printf 的任务用这个值必爆"？
12. 为什么 CM0+ 上的 HardFault 比 CM3 上难定位？你能用什么替代手段？

<details>
<summary>答案要点（点开对答案）</summary>

1. R0,R1,R2,R3,R12,LR,PC,xPSR。R4–R11 是"被调用者保存"寄存器，硬件不负责，由软件（`xPortPendSVHandler` 里的 4+4 条存取指令）保存。
2. 返回 Thread 模式、**使用 PSP**、带基本上下文。它在 **LR** 里（异常进入时硬件写入）。
3. Handler 模式架构上强制用 MSP，所以 ISR 用主栈、任务用各自 PSP 栈，天然隔离。好处：任务栈不用为 ISR 预留深度，任务栈大小只按任务自身需求算。
4. bit24 = T 位（Thumb）。CM0+ 只有 Thumb 指令，置 0 会立刻违反架构 → HardFault。
5. 不用。CM0 端口在 `xPortStartScheduler()` 里**直接调用** `prvPortStartFirstTask()`，里面用纯软件方式（`msr psp` + `msr CONTROL` + `pop` + `bx`）构造现场。`vPortSVCHandler` 是历史遗留的空函数。
6. EXC_RETURN（`0xFFFFFFFD`）。所以 `bx r3` 是"从异常返回"，硬件随后从新 PSP 弹出 8 字帧并跳到新任务。
7. 使切换请求被推迟到所有 ISR 执行完，中断实时性不受任务切换影响；同时避免 tick 打断高频外设中断；二者同级也不会互抢。
8. 临界区只能"关全部中断"，无法只屏蔽低优先级。串口接收中断在任何一个内核/用户临界区内都会被延迟 → 长临界区会导致串口 DMA 完成/溢出事件响应不及时 → 必须短临界区 + DMA 缓冲。
9. 因为 CM0（ARMv6-M）没有 BASEPRI 寄存器，只能用 PRIMASK 全屏蔽；CM3（ARMv7-M）可用 BASEPRI 只屏蔽到某级别以下。
10. 会落到 `prvTaskExitError()`（初始 LR 被设为该函数）→ 触发断言/死循环。因为任务不是在"被调用"的语境里运行的，`bx` 进场后没有合法的返回地址。
11. 128 字 × 4 字节 = **512 字节**。任务帧本身就占 17 字（68B），加 `printf`（可能带软浮点、格式化缓冲）轻松超过几百字节 → 爆栈。必须实测 + 放大 + 留 30% 余量。
12. ARMv6-M 没有 CFSR/HFSR/BFAR 等故障状态寄存器，查不到原因。替代：解析压栈帧里的 PC/LR 反推现场；用 `vApplicationStackOverflowHook`、`uxTaskGetStackHighWaterMark`、`configASSERT`、以及"任务的 PC/LR 打点"等手段主动防御。

</details>

## 9. CM0+ vs CM3/M4 差异速查表（★贴工位墙上）

| 对比项 | **CM0+ / ARMv6-M（你的片子）** | CM3/M4 / ARMv7-M（多数教程的板子） |
|---|---|---|
| 中断优先级位数 | **2 位 (4 级)** | 通常 4 位 (16 级) |
| 可屏蔽中断数 | 32 | 240 |
| **BASEPRI** | ❌ 无 → 临界区 = **全关中断** | ✅ 有 → 可分级屏蔽 |
| `configMAX_SYSCALL_INTERRUPT_PRIORITY` | **不适用**（端口里 0 引用） | 必须正确设置 |
| `configKERNEL_INTERRUPT_PRIORITY` | **不参与运算**（硬编码 255） | 用它设内核优先级 |
| `vPortValidateInterruptPriority()` | ❌ 无（ISR 误用 API 不会被断言拦截） | ✅ 有 |
| 启动第一个任务 | 直接函数调用，**不用 SVC** | `svc 0` |
| Fault 种类 | **只有 HardFault** | MemManage/BusFault/UsageFault + HardFault |
| 故障状态寄存器 | ❌ 无 CFSR/HFSR/BFAR | ✅ 有（定位神器） |
| **VTOR（向量表重定位）** | ❌ 无（IAP 需靠 MEM_MODE / SRAM 启动） | ✅ 有 |
| 硬件原子指令 | ❌ 无 LDREX/STREX | ✅ 有 |
| DWT 周期计数器(CYCCNT) | ❌ **无**（手册第35章：只有 2 个 watchpoint + DWT_PCSR） | ✅ 有 → 可用它做 `configGENERATE_RUN_TIME_STATS` |
| FPU | ❌ 无（CONTROL 无 FPCA 位） | M4F/M7 有 |
| MPU | 可选，**本芯片按无对待** | 可选，常用来做栈保护 |
| 异常返回特殊值 | 0xFFFFFFF1/F9/FD | 另有 E1/E9/ED（带 FPU 现场） |
| 异常进入对齐 | **强制 8 字节对齐**（不可关） | 可配置（CCR.STKALIGN，默认开） |

⚠️ **由上表推出的两个实操提醒**：
1. **DWT 没有 CYCCNT** → 想统计各任务 CPU 占用率，`configGENERATE_RUN_TIME_STATS` **不能配成 DWT 模式**，必须用硬件定时器（选一个不用的 TIM，配置为自由运行的高分辨率计数器，在 `portCONFIGURE_TIMER_FOR_RUN_TIME_STATS()` 里初始化）。
2. **IAP 跳转方案要重新审视** → 你的 IAP 是"整包升级 + 跳转到应用"，在没有 VTOR 的 CM0+ 上，"应用向量表必须在 0x00000000"这件事**必须显式保证**（靠 BOOT_LOCK 选项字节或 `SYSCFG_CFGR1.MEM_MODE` 重映射），否则中断会全部跳错地方。这是阶段 5「IAP 与 RTOS 共存」的必查项。
