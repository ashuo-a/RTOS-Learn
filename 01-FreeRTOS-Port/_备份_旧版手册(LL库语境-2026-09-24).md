## §1 移植前唯一必须做的决策：编译器 → 端口

Cortex-M0+ 的 FreeRTOS 端口有 3 份，**选错就编译不过**。判断依据不是你的喜好，是编译器：

| 你的编译器 | 用哪个端口 | 官方原话（源码里就这么写的） |
|---|---|---|
| **AC5 (armcc)** | `portable/RVDS/ARM_CM0/` | `portable/Keil/See-also-the-RVDS-directory.txt` |
| **AC6 (armclang)** | `portable/GCC/ARM_CM0/` | `portable/ARMClang/Use-the-GCC-ports.txt`：<br>*"The FreeRTOS GCC port layer also builds and works with the ARMClang compiler. To use the ARMClang compiler build the port files from FreeRTOS/Source/portable/GCC."* |
| GCC (非 Keil) | `portable/GCC/ARM_CM0/` | 同上 |

**为什么 AC6 不能用 RVDS 端口？** 实测 `RVDS/ARM_CM0/port.c` 通篇是这种写法：

```c
__asm void xPortPendSVHandler( void )      /* ← AC5 的"嵌入式汇编函数"语法 */
{
    ...
}
```

`__asm void f(void){...}` 是 armcc（AC5）的私有扩展，**armclang 不支持**，用 AC6 编会直接报语法错误。而 GCC 端口用的是 armclang 认得的写法：`__attribute__((naked))` + `__asm volatile("...")`。

> **建议路径**：既然 Puya 官方模板本来就是 AC5（`<uAC6>0</uAC6>`），**先用 RVDS 端口 + AC5**，这条路上没有已知障碍。将来要迁 AC6 时，只需把工程里 `RVDS\ARM_CM0` 那两个文件换成 `GCC\ARM_CM0` 的，其余一行不用改。

## §3 第一道坎：两个必踩的坑

### §3.1 ★三个符号冲突 → `L6200E: Symbol multiply defined`

官方模板的 `Src\py32l090_it.c` 里有这么三个**空函数**：

```c
void SVC_Handler(void)      { }
void PendSV_Handler(void)   { }
void SysTick_Handler(void)  { }
```

而 FreeRTOS 的 `port.c` 里也有（通过 `FreeRTOSConfig.h` 映射成同样的名字）：

- `xPortPendSVHandler` → 映射为 `PendSV_Handler`
- `xPortSysTickHandler` → 映射为 `SysTick_Handler`

**两个 `.c` 定义了同名函数 → 链接器报 L6200E。** 处置（`py32l090_it.c`）：

```c
/* ★ 移植 FreeRTOS：这三个空函数必须让位，否则与 port.c 撞符号
   原内容保留在注释里，将来要退回裸机时改回来即可 */

/* void SVC_Handler(void) {} */        /* CM0+ 端口不使用 SVC，这个留着也行，
                                          但前提是——别在 FreeRTOSConfig.h 里
                                          定义 vPortSVCHandler 的映射 */
/* void PendSV_Handler(void) {} */     ★必须注释掉
/* void SysTick_Handler(void) {} */    ★必须注释掉
```

> 我在 `FreeRTOSConfig.h` 里**故意没有**定义 `vPortSVCHandler` 映射，就是为了让 `it.c` 的空 `SVC_Handler` 继续存在、不产生冲突。CM0+ 的 FreeRTOS 端口不用 SVC 指令（任务启动走的是 `svc 0`？不是 —— CM0 端口通过修改栈帧 + `bx` 直接启动第一个任务，不靠 SVC），这点和 M3/M4 教程讲的不一样，**别照着 M4 的教程去找 SVC_Handler**。

### §3.2 ★把中断用的栈（MSP）加大

启动文件里默认 `Stack_Size EQU 0x00000400`（1KB）。裸机时 1KB 也许勉强够，**跑 RTOS 之后所有中断都在这个栈上执行**，而且你的 ISR 可能调用 `xQueueSendFromISR` 等内核函数。建议：

```asm
Stack_Size      EQU     0x00000800      ; 2KB，给中断用
```

> 注意区分两个"栈"，这是新手最容易混的一对概念：
> - **MSP（主栈）** = 启动文件里的 `Stack_Size`，**中断和启动代码用**，RTOS 下不再给任务用。
> - **任务栈** = `xTaskCreate()` 的第 3 个参数，单位是**字（word=4 字节）**，从 FreeRTOS 堆里分配。
>
> 例：`xTaskCreate(f, "t", 128, NULL, 1, NULL)` → 该任务栈 = 128 × 4 = **512 字节**。

## §4 FreeRTOSConfig.h：每一项为什么这么写

配置全文见 `D:\RTOS-Learn\01-FreeRTOS-Port\PY32L090_FreeRTOS\Config\FreeRTOSConfig.h`（已按 PY32L090 调好，可直接用）。这里只讲**记忆点和陷阱**。

### §4.1 CM0+ 专属：三个"配了也白配"的宏

全网 M3/M4 教程都会让你配这三个，**在 CM0+ 上它们全都无效**：

| 宏 | 为什么在 CM0+ 上无效 |
|---|---|
| `configKERNEL_INTERRUPT_PRIORITY` | CM0 端口把内核异常优先级**硬编码写死**为最低（实测 `port.c` 里：`#define portMIN_INTERRUPT_PRIORITY ( 255UL )`，直接写进 SHPR3），不看这个宏 |
| `configMAX_SYSCALL_INTERRUPT_PRIORITY` | ★CM0 **没有 BASEPRI 寄存器**，FreeRTOS 无法"只屏蔽某优先级以下的中断"，这个宏压根没有实现 |
| `configPRIO_BITS` / `configLIBRARY_MAX_SYSCALL_INTERRUPT_PRIORITY` | M3/M4 端口用它做优先级反向移位，CM0 端口无此逻辑 |

**由此推出的最重要结论（阶段2 会反复用到）**：

> CM0+ 上 `taskENTER_CRITICAL()` 展开成 **`CPSID i`（关掉全部中断）**，不是像 M3/M4 那样只关一部分。
> 所以 CM0+ 上唯一的纪律是：**中断服务函数必须极短**。你在 ISR 里多跑 100us，全局的中断延迟和节拍精度就都受影响。

### §4.2 必定义的 6 个宏（漏了必报 `#error`）

FreeRTOS.h 会主动检查并 `#error` 报错（实测源码 line 135~159）：

```c
configMINIMAL_STACK_SIZE   /* 单位=字！空闲任务栈。写 128 = 512 字节 */
configMAX_PRIORITIES       /* 任务优先级的"软件"档数，见下 */
configUSE_PREEMPTION       /* 1=抢占式 */
configUSE_IDLE_HOOK        /* 1/0 */
configUSE_TICK_HOOK        /* 1/0 */
configUSE_16_BIT_TICKS     /* 0（用 32 位节拍）*/
```

**一个反直觉的点**：`configMAX_PRIORITIES = 8` 在 CM0+ 上完全合法。CM0 只有 2 位硬件优先级（4 档），但那是**给中断用的**；任务的优先级是 FreeRTOS 用就绪链表软件实现的，档数随便你要（8 也够，32 也行，只是每档多占一点 RAM）。

### §4.3 内存管理：为什么选 heap_4 + 8KB

| 方案 | 特点 | 适用 |
|---|---|---|
| heap_1 | 只分配不释放，最简单，无碎片 | 所有任务/队列开局建好、永不删除 → **量产首选** |
| heap_2 | 能释放但**不合并**碎片 | 已过时，别用 |
| **heap_4** | 能释放 + **相邻块自动合并** | ★学习期用这个，动态创建/删除任务不炸 |
| heap_5 | heap_4 + 支持多块不连续内存 | SRAM 分段时用 |

`configTOTAL_HEAP_SIZE = 8 * 1024`。堆不是从启动文件的 `Heap_Size` 来的，而是 heap_4.c 里一个静态数组（进 `.bss`），**跟 `Heap_Size 0x200` 没关系**。

### §4.4 ★32KB SRAM 的预算表（重要，别让堆把内存吃光）

| 项目 | 占用 | 备注 |
|---|---|---|
| FreeRTOS 堆（`configTOTAL_HEAP_SIZE`） | 8192 B | 所有任务栈 + 队列 + 信号量都从这里出 |
| MSP 主栈（启动文件 `Stack_Size`） | 2048 B | 中断用 |
| 全局/静态变量（含你的传感器缓冲、参数区） | 看你工程 | **先去看 `.map` 文件的 `Total RW Size`** |
| 空闲任务栈 | 512 B | 从上面那 8KB 里出 |
| 本例 4 个任务栈 | 128+128+256+128 字 = **2560 B** | 从上面那 8KB 里出 |

**开工前的第一件事**：编译一次你现有的裸机工程，打开 `.map` 文件看 `Total RW Size (RW Data + ZI Data)` 是多少，用 `32768 - 这个值` 才是你能给 RTOS 的总量，再从中划 8KB 给堆。**STM32F103C8 那种 20KB SRAM 的教程数字（比如堆给 10KB）不能照抄。**

### §4.5 调试期必须全开的两个开关

```c
#define configCHECK_FOR_STACK_OVERFLOW   2   /* 2=哨兵值法，任务栈快溢出就能抓到 */
#define configUSE_MALLOC_FAILED_HOOK     1   /* 堆耗尽立刻报出来，而不是返回 NULL 后跑飞 */
#define configASSERT( x )  if((x)==0){ vApplicationAssertFailure(__FILE__,__LINE__); }
```

这三个开关打开后，内核会去调用 `vApplicationStackOverflowHook` / `vApplicationMallocFailedHook` / `vApplicationAssertFailure` —— **你不实现就报 `L6218E: Undefined symbol`**。这就是 §7.2 那个 `app_rtos_hooks.c` 存在的原因：它不是"可选增强"，是移植的最后一块拼图。

## §5 ★时钟与 SysTick 的交接（最容易埋雷的一节）

### §5.1 官方库自己就说了"用 RTOS 时别调它"

实测 `py32l090_ll_utils.c` 第 148~155 行，`LL_Init1msTick` 的官方注释原文：

> `@note When a RTOS is used, it is recommended to avoid changing the Systick`
> `configuration by calling this function, for a delay use rather osDelay RTOS service.`

`LL_mDelay` 的注释原文（第 162~170 行）：

> `@note When a RTOS is used, it is recommended to avoid using blocking delay`
> `and use rather osDelay service.`

**而官方 LL 模板的 `main.c` 第 86 行正好就写了这行必须删的代码：**

```c
LL_Init1msTick(8000000);      /* ★删掉它 */
```

**为什么必须删**（不是说它会让芯片死机，而是会**让时间全错**）：

- 它把 SysTick 重配成 `8000000/1000-1 = 7999` 的重载值，即 8MHz 下 1ms 一跳。
- 但 FreeRTOS 在 `xPortStartScheduler()` 里会重新配置 SysTick 为 `configSYSTICK_CLOCK_HZ / configTICK_RATE_HZ - 1`。你的板子跑 72MHz，所以应该是 **71999**。
- 顺序上一旦有人在**调度器启动之后**（比如某个任务里、或某次重新初始化时）调了它 → SysTick 重载被改回 7999 → 节拍变成 72MHz/8000 = **9kHz**，于是**所有 `vTaskDelay(1000)` 变成约 111ms**，看起来就是"程序莫名快得离谱 / 串口乱码 / 传感器时序崩了"。

### §5.2 `LL_mDelay` 在 RTOS 下还能用吗？

实测它的实现（`py32l090_ll_utils.c` 第 171~191 行）是**轮询 SysTick 的 COUNTFLAG 标志**：

```c
while (tmpDelay != 0U) {
    if ((SysTick->CTRL & SysTick_CTRL_COUNTFLAG_Msk) != 0U) { tmpDelay--; }
}
```

所以在 FreeRTOS 下它**不会崩**（SysTick 还在 1ms 跑），但它是个**纯 CPU 死等循环**：

- 在任务里用它 = 这段时间 CPU 被这个任务霸占，**其他任务全部得不到执行**，RTOS 的意义直接归零。
- 结论：**任务里一律用 `vTaskDelay(pdMS_TO_TICKS(n))`**；`LL_mDelay` 只允许在**调度器启动之前**的初始化代码里用（那时还没有任务）。

### §5.3 正确的启动顺序

```
上电
 └─ 启动文件：SystemInit()  →  ★实测：官方模板的 SystemInit 只做最基础的准备，
    │                          真正的时钟配置在 main 里由 APP_SystemClockConfig() 做
    └─ main()
       ├─ ① 时钟配置  ← ★见 §5.5，这里必须先想清楚是 8MHz 还是 72MHz
       ├─ ② 板级外设初始化（GPIO / UART / 传感器……）★这里还可以用 LL_mDelay
       ├─ ③ 创建任务 xTaskCreate(...)              ★必须在④之前
       └─ ④ vTaskStartScheduler()  ← 这一句之后：
                                    · 创建空闲任务
                                    · 设置 PendSV/SysTick 优先级 = 最低
                                    · 接管 SysTick（重载值 = configSYSTICK_CLOCK_HZ/1000-1）
                                    · 启动第一个任务
                ★永不返回（返回了 = 堆不够、空闲任务没建起来）
```

### §5.4 三个禁止动作（记在脑子里）

1. **禁止**在调度器启动后调用 `LL_Init1msTick()` / `HAL_Init()`（都会重配 SysTick → 节拍崩）。
2. **禁止**在任务里用 `LL_mDelay()`（死等，饿死其他任务）。
3. **禁止**直接改 `SysTick->LOAD` / `SysTick->CTRL`（这是内核的财产了）。

> 想确认没踩雷：调试器里看 `SysTick->LOAD (0xE000E014)` 必须是 **71999**（72MHz 板子）。

### §5.5 ★主频对齐：8MHz 还是 72MHz，必须先定下来

这是本手册实测出来的**最隐蔽的一个坑**。官方 LL 模板（`PY32L090xx_Templates_LL\Src\main.c` 第 66~90 行）的时钟配置长这样：

```c
static void APP_SystemClockConfig(void)
{
  LL_RCC_HSI_Enable();
  LL_RCC_HSI_SetCalibFreq(LL_RCC_HSICALIBRATION_8MHz);      /* HSI 8MHz */
  ...
  LL_RCC_SetSysClkSource(LL_RCC_SYS_CLKSOURCE_HSISYS);      /* 直接拿 HSI 当系统时钟 */
  ...
  LL_Init1msTick(8000000);                                  /* ★要删的这行 */
  LL_SetSystemCoreClock(8000000);                           /* ★模板主频 = 8MHz，没开 PLL */
}
```

**也就是说：模板根本没用 PLL，板子跑 8MHz。** 而你自己的产品工程（WX_LowCost / 燃气报警器）是 72MHz（`pll.c`）。这两条路的 `configCPU_CLOCK_HZ` **不一样**：

| 方案 | 时钟怎么配 | `configCPU_CLOCK_HZ` | 适用 |
|---|---|---|---|
| **A（推荐）** | 用你现有产品工程的时钟代码：`MCUPllCfg()` / `Init_SysClk_Gen(1,72)` + `pll.c` | `72000000UL` | 想把阶段2~5 直接接到真实产品上 |
| **B** | 照官方 LL 模板，`APP_SystemClockConfig()` 保持不动（只删 `LL_Init1msTick` 那行） | `8000000UL` | 只想先跑通、不追求性能 |

**写错的症状特征**（记住它，能省你半天调试）：

- 不是死机、不是 HardFault，而是**一切时间都快 9 倍**；
- 72MHz 板子 + `configCPU_CLOCK_HZ=8000000` → SysTick 重载 = 7999 → 实际 72MHz/8000 = **9kHz** 节拍 → `vTaskDelay(1000)` 只等约 111ms；
- 串口打印刷屏特别快、LED 闪得比预期急、传感器应答超时对不上。

**唯一可靠的验证方法**：调试器 Watch 窗口加 `SystemCoreClock`，它必须 **等于** `configCPU_CLOCK_HZ`。

| 检查项 | 期望 |
|---|---|
| `SystemCoreClock` | 必须 == `configCPU_CLOCK_HZ`（72MHz 方案 = 72000000） |
| `SysTick->LOAD` (0xE000E014) | `SystemCoreClock / 1000 - 1`（72MHz → **71999**） |

## §6 中断移植规范

### §6.1 ISR 标准模板（FromISR 版本 + 退出时切任务）

`FreeRTOSConfig.h` 里已经给 `portYIELD_FROM_ISR()` 准备了实现（实测 `portmacro.h`：`#define portYIELD_FROM_ISR( x ) portEND_SWITCHING_ISR( x )`）。所有中断服务函数照这个骨架写：

```c
/* ★向量名以启动文件/你工程实际名字为准 */
void xxx_IRQHandler(void)
{
    BaseType_t xHigherPriorityTaskWoken = pdFALSE;   /* ① 必须初始化 */

    /* ② 清标志 + 取数据（尽量短，CM0 上临界区是全屏蔽中断） */
    if (LL_EXTI_IsActiveFlag_0_31(LL_EXTI_LINE_0) != RESET)
    {
        LL_EXTI_ClearFlag_0_31(LL_EXTI_LINE_0);

        /* ③ 用带 FromISR 后缀的 API 通知任务 */
        xTaskNotifyFromISR( xWakeTask, 1, eSetBits, &xHigherPriorityTaskWoken );
    }

    /* ④ 如果唤醒了更高优先级任务，立刻切；否则什么也不做（这句不能省） */
    portYIELD_FROM_ISR( xHigherPriorityTaskWoken );
}
```

**铁律**：ISR 里只能调用名字带 `...FromISR` 的 API（`xQueueSendFromISR` / `xSemaphoreGiveFromISR` / `xTaskNotifyFromISR`）。在 ISR 里调 `vTaskDelay` / `xQueueSend` 这类非 FromISR 版本 → 直接 `configASSERT` 失败或跑飞。

### §6.2 优先级怎么分（CM0 只有 4 档：0/1/2/3）

| 优先级 | 给谁 | 理由 |
|---|---|---|
| 0（最高） | 安全相关：掉电检测、过流/阀门急停 | 必须最先响应，能抢占其他所有中断 |
| 1 | 串口/传感器接收 | 有硬件缓冲，稍慢也能救 |
| 2 | 普通定时器、按键 | 容忍几十 us 延迟 |
| **3** | **★不要给外设** | PendSV / SysTick 占着 3（内核异常必须最低），外设挤进来会拖慢任务切换 |

**和 M3/M4 教程最大的不同**：M4 教程会让你"把外设优先级设为 `configMAX_SYSCALL_INTERRUPT_PRIORITY` 以下"，**CM0 上这句话没有意义**（没有 BASEPRI）。CM0 上你能做的只有两件事：**用 0~2 给外设**，以及**把 ISR 写短**。

### §6.3 你那类产品要特别注意的：

- **掉电检测 ISR**：只置标志 / `xTaskNotifyFromISR` 唤醒一个高优先级任务，**绝不要在 ISR 里做 Flash 写、参数保存、打印**（这些几百 us 到几 ms，会直接把节拍拖崩）。
- **看门狗**：RTOS 下"在哪喂狗"要重新设计（空闲钩子里喂狗 = 高优先级任务死循环时反而喂不上，这既是坑也是检测手段）。阶段3/5 再定，阶段1 先不要开 IWDG。

### §7.2 `app_rtos_hooks.c` 不是可选的

它实现了 §4.5 三个开关要求你提供的钩子函数，外加两个调试工具：

| 函数 | 什么时候被调用 | 该怎么用 |
|---|---|---|
| `vApplicationAssertFailure` | 任何 `configASSERT` 失败 | 调试期死在这里看 Call Stack；量产改 `NVIC_SystemReset()` |
| `vApplicationStackOverflowHook` | 切换任务时发现栈尾哨兵被改写 | 打印是哪个任务 → 回去加大它的栈 |
| `vApplicationMallocFailedHook` | 堆分配失败 | 打印剩余堆 → 加大 `configTOTAL_HEAP_SIZE` |
| `vApplicationIdleHook` | 所有任务都在阻塞时 | ★不能阻塞、不能 `vTaskDelay`；阶段4 在这里做低功耗 |
| `vApplicationTickHook` | **在 SysTick 中断里** | ★中断上下文：不能阻塞、不能 printf 长输出 |
| `RTOS_PrintTaskList()` | 你主动调用 | `vTaskList` 输出所有任务状态 |
| `RTOS_PrintStackWaterMark()` | 你主动调用 | 堆余量 + 栈水位 |

> 文件顶部唯一要改的地方是 `APP_LOG` 宏：换成你工程里现成的串口打印函数（如 `Debug_Printf`）。你现在还没有串口打印的话，把它定义成空 —— 钩子改成点灯/死循环一样能定位问题。

## §8 验收清单（★拿调试器实测，不要"看着像在跑"）

逐条勾，每条都能给出**具体数值证据**：

| # | 检查项 | 怎么看 | 期望结果 |
|---|---|---|---|
| 0 | ★主频和配置对齐 | 调试器 Watch 加 `SystemCoreClock` | **必须 == `configCPU_CLOCK_HZ`**。72MHz 方案的裸机代码 + `8000000UL` 的配置 = 全部时间快 9 倍（§5.5） |
| 1 | 内核节拍周期正确 | 调试器看 `0xE000E014` (`SysTick->LOAD`) | **71999**（= `configSYSTICK_CLOCK_HZ/1000-1`） |
| 2 | 内核异常优先级最低 | 看 `0xE000ED20` (`SHPR3`) | **0xC0C00000**（PendSV=0xC0、SysTick=0xC0；写的是 255，CM0+ 只实现高 2 位，读回即 0xC0） |
| 3 | 临界区没漏配对 | Watch 窗口加 `uxCriticalNesting` | 稳态下 **0**；>0 说明某处 `taskENTER_CRITICAL` 没配 `EXIT` |
| 4 | 调度器在切任务 | 全速运行时暂停，看 Call Stack | 栈里出现 `xPortPendSVHandler` / `prvPortStartFirstTask` 之一 |
| 5 | 两个 LED 独立 | 串口打印的 toggle 时间戳 | led1 间隔 ~500ms、led2 ~300ms，**互不影响**（裸机排队式软定时器做不到这点） |
| 6 | 堆没吃光 | `RTOS_PrintStackWaterMark()` 的 `minEver` | 明显 > 0（比如 >1KB）。**贴到 0 = 迟早 `MALLOC FAILED`** |
| 7 | 任务栈都够 | `vTaskList` 的 Stack 列（剩余字数） | 每个任务剩余 **> 30 字**（≈120B）。低于 20 就加大它 |
| 8 | 运行期动态创建成功 | 第 10 秒串口出现 `[born] 我是启动后动态创建的任务...` | 出现 = 调度器一直活着、堆够用、`vTaskDelete` 正常 |

**第 2 条的 0xC0C00000 是怎么算出来的**（你以后调优先级会用到）：CM0+ 只实现 2 位优先级，即每 8 位优先级字段里只有高 2 位（bit7:6）有效，写 `0xFF` 实际落下的是 `0b11`，读回就是 `0xC0`。`SHPR3` 里 PendSV 在 [23:16]、SysTick 在 [31:24]，故为 `0xC0C00000`。

### §12.2 坑 1：官方例程一拷出来，相对路径就断了

`Project.uvprojx` 里写的是：

```
..\..\..\..\..\..\Drivers\PY32C882_HAL_Driver\Inc
```

六层 `..\` 是为了从 `Projects\PY32C882-STK\Example\GPIO\GPIO_Toggle\MDK-ARM` 上溯到固件根目录。**一旦把工程拷到别处（比如你的学习工作区），这个路径就解析到 `D:\Drivers` —— 不存在**，工程直接编不过。

**处置**：把精简驱动树拷进工程目录，路径改成两层：

```
GPIO_Toggle\
├── Drivers\CMSIS\Include\                 (30 文件)
├── Drivers\CMSIS\Device\PY32C882\Include\ (3 文件)
├── Drivers\PY32C882_HAL_Driver\{Inc,Src}\ (72+62 文件)
└── Drivers\BSP\PY32C882xx_Start_Kit\      (4 文件)
```

⇒ include 路径全部变成 `..\Drivers\...`，工程从此**自包含、可整体搬移**。（不用拷整个 13.5MB 的 `Drivers`，上述 5 个子目录共 171 个文件足够。）

> 检查手法：`[System.IO.Path]::GetFullPath($path)` 能一眼看出相对路径实际指向哪。

### §12.3 坑 2：HAL 工程的 `HAL_IncTick()` 必须"交接"，否则 HAL 的时基静默死掉

官方 `Src\py32c882_it.c` 里是这样：

```c
void SysTick_Handler(void)
{
  HAL_IncTick();          /* ← HAL 的 1ms 时基靠这个维持 */
}
```

而 RTOS 接管 SysTick 后，这个函数必须让位给 `xPortSysTickHandler`。**如果只是简单地注释掉它，HAL 侧不会报任何错，但**：

- `HAL_GetTick()` 永远返回 **0**
- `HAL_Delay(n)` **永不返回**（死等）
- `HAL_UART_Transmit(&h, ..., 1000)` 之类带超时的 HAL 调用**全部立即超时**

**处置**：把 `HAL_IncTick()` 搬进 tick 钩子，让 HAL 时基与 RTOS 节拍同源：

```c
/* Src\app_rtos_hooks.c */
void vApplicationTickHook(void)      /* configUSE_TICK_HOOK 必须为 1 */
{
    HAL_IncTick();
}
```

这条是**HAL 库工程接 RTOS 的通用规律**：LL 裸机工程没有 HAL 时基，就不存在这个问题；凡是用 HAL 的工程都要做这一步。

### §12.4 坑 3：`configMINIMAL_STACK_SIZE` —— 本次真的漏了

第一次 `UV4 -b` 编译结果是 **8 errors**，全部是同一句：

```
..\FreeRTOS\include\FreeRTOS.h(135): error: #35: #error directive:
Missing definition: configMINIMAL_STACK_SIZE must be defined in FreeRTOSConfig.h.
```

`tasks.c / queue.c / list.c / timers.c / heap_4.c / port.c / main.c / app_rtos_hooks.c` 8 个文件一起报（因为它们都 include `FreeRTOS.h`）。补上 `#define configMINIMAL_STACK_SIZE ( 128 )` 即解决。

> **教训**：§4.2 那 6 个必定义宏，一个都不能少。写配置时**逐个对一遍**比事后看报错快。

### §12.6 命令行编译验证法（本次验收就靠它，强烈建议你用）

不用开 Keil GUI，直接命令行出结果：

```powershell

$proj = 'D:\RTOS-Learn\01-FreeRTOS-Port\GPIO_Toggle\MDK-ARM\Project.uvprojx'
```

1. 日志文件是 **UTF-16(BE) 无 BOM** 编码，用记事本打开正常，用普通 `Get-Content`/Python 按 UTF-8 读会全是乱码——要按 UTF-16BE 解码（本次写了个 `readtxt.py` 专门干这个）。
2. Keil GUI 里如果打开着同一工程，命令行编译会失败；先关掉 GUI。

### §12.7 上板验收清单（编译通过只是"能跑"的前提，不是结论）

| # | 现象 | 期望 |
|---|---|---|
| 1 | LED3 (PA2) | 每隔 250ms 翻转 = **2Hz**，与改之前的裸机版肉眼一致（说明 RTOS 没改变原有功能） |
| 2 | 串口 115200 (PB9=TX) | 上电打印 `SystemCoreClock = 8000000 Hz (configCPU_CLOCK_HZ = 8000000 Hz)` |
| 3 | 串口每秒 | `[t=xxxxms] tasks=3 freeHeap=xxxxB ledStackMinFree=xx words`，`t` 每次递增 1000 左右 |
| 4 | 串口每 5 秒 | 任务表：应有 `led / log / IDLE` 三行，**IDLE 也在**（证明调度器真的在跑） |
| 5 | `SysTick->LOAD` (0xE000E014) | **7999**（= 8MHz/1000-1；若是 71999 说明主频配置想成 72MHz 了） |
| 6 | `SHPR3` (0xE000ED20) | **0xC0C00000** |
| 7 | `freeHeap` | 明显大于 0（8KB 堆减去任务栈后的余量）；`ledStackMinFree` > 30 字 |
